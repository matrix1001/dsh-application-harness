## 事实优先级

发生冲突时按以下顺序处理，不靠猜测哪份更新：

1. 具体类型、字段、默认值：源码和测试；
2. 当前行为：架构总览、实现细节与测试；
3. 目标设计：`docs/architecture/` 下的设计专题；
4. 操作步骤：应用开发指南；
5. 使用方式：README。

设计专题描述目标，不自动等于当前实现；架构总览与实现细节描述现状，不自动推翻已确认的目标。两者的差异必须显式修复，或在实现细节中标注边界。

## 维护规则

- 先改对应专题，再同步实现架构、应用开发指南和代码；不要在多篇里复制同一规则。
- 字段和签名指向源码，行为指向测试，设计边界写在专题，操作步骤写在指南。
- 未来能力必须标成目标或边界，不能写成已实现；已完成的实现细节放实现细节或源码。
- 不新增临时计划、历史归档或按日期命名的副本；历史通过 Git 查询。
