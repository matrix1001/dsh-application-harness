## 3. 事实归属

一条事实只有一个家，其他位置不重复定义。发生冲突时按这张表判断权威，不靠猜哪份更新。

| 事实 | 唯一归属 | 不属于这里 |
|---|---|---|
| 字段、签名、默认值、类型定义 | 源码 | 设计专题、README |
| 错误码语义、宿主状态文件、符号入口 | [REFERENCE](REFERENCE.md) | 实现细节、开发、安装与发布 |
| 当前实现的完整描述、与目标的差距、验收边界 | [实现细节与验收](architecture/11-实现与验收.md) | 设计专题、README |
| 操作所需的当前事实（接口用法、命令、可用能力） | 任务指南、操作手册、上手、参考 | 设计专题 |
| 目标规则的完整定义与取舍 | 设计专题 1–10、12 | 实现细节、README |
| 开发、发布与升级的命令流程 | [上手](START.md)、[操作手册](DEVELOPMENT.md) | 其他文档（AGENTS 只留速查） |
| 修改前必须知道的规则 | [AGENTS](../AGENTS.md) | docs 下的任何一篇 |
| 安装与使用 | [README](../README.md)（是什么、最短安装入口与使用方式） | 设计专题 |
| Release 校验、升级、卸载与版本差异 | [操作手册 §3](DEVELOPMENT.md#3-安装-release) | 设计专题；README 只保留一句摘要 |
| 文档索引与写法 | 本页 | README、架构总览 |

状态只标类型。设计专题只写目标，不写现状；任务指南、操作手册、上手和参考可以写操作所需的当前事实，也可以用操作步骤复述规则，但不写易变数字和版本。与目标的差距和验收边界仍只写在《实现细节与验收》，其他篇链接。

## 4. 写作与维护

- **一条事实一处。** 新规则先放到它所属的那一篇，其他位置只留链接或操作化复述。
- **段落不超过 300 字。** 长规则拆成列表或表格；预算是棘轮，只能降不能升（`scripts/doc-budget.json`）。
- **不写易变数字。** 应用数、包数、会话上限这类数字不写进正文；能由脚本核对的交给脚本，不能核对的不写。
- **类型标记。** 用 `> 类型：目标设计。` 这样的固定句，句子后面不附任何会过期的事实；状态归属见第 3 节。
- **术语以[用词约定](architecture/1-总体设计.md#用词约定)为准。** 被替换的说法会由文档测试拦住。
- **新文档必须在本页登记**，否则 `check:docs` 失败；废弃文档不建归档，历史看 Git。
- **跨三个模块以上的流程配一张图**；枚举用表，解释用短段落。
- **校验命令是 `pnpm run check:docs`。** 它证明项目文档的链接、锚点、命令名、登记和字数合规，以及 skill 文档的链接、锚点与命令名；不证明内容正确，事实仍由评审负责。
