# 应用结构与运行

[总体设计](1-总体设计.md) · [用词约定](1-总体设计.md#用词约定) · 本篇定义应用组成、运行和数据边界；数据结构遵循[统一 JSON 协议](2-统一JSON协议.md)。

## 应用是什么

应用是围绕明确业务职责组织的单元，拥有稳定身份、业务规则与状态解释权，由应用后端提供应用操作，并按需提供应用前端。它不是页面、会话或工作区的别名。

最小应用只需身份、应用操作声明和实现，对外开放另行声明。平台为无持久数据、无前端、无额外能力的应用提供明确默认值，不要求它接入数据库或模型。

| 声明部分 | 必要内容 |
|---|---|
| 身份 | `appId`、名称、用途、软件版本；注册时禁止身份冲突 |
| 应用操作 | 第 2 篇定义的声明集合，按名称绑定应用后端的业务函数 |
| 协作 | 明确目标应用、操作；按需声明状态刷新订阅，见第 6 篇 |
| 平台能力 | 使用模型、网络、凭据和进程等已提供能力的需求 |
| 数据 | 无数据，或标准存储、独立文件／数据库／外部服务的使用方式、位置、业务版本、备份与导入导出边界 |
| 可选接入 | 对象类型、事件、业务页面、设置页面、生命周期钩子 |

应用声明包含可序列化信息，运行实现包含函数与资源。声明只说明需求，不授予权限。能力声明是应用版本的一部分，安装和更新时整体校验；应用不能在运行中动态申请未声明能力。界面按钮可以组合应用操作，内部函数不必全部接入平台。

应用设置属于应用管理的业务数据，由应用定义字段、默认值、校验和生效规则并负责保存。平台管理的操作策略、平台能力授权、订阅授权、模型选择和凭据不属于应用设置；应用设置不能改变这些平台规则或替代凭据。

一个宿主内每个 `appId` 只注册一个平台应用实例。第一版按单用户应用建模，不在平台协议中表达多账户、组织或业务空间；后续出现真实需求时再增加实例身份、数据分区和实例级权限。

## 应用项目组织

第一版应用由本仓 workspace 包交付：应用声明与后端在宿主包中，可选的业务页面在视图包中；部署声明决定哪些包进入组合。应用不是任意源码目录的别名。开发会话以本仓源码根为工作区，焦点是该应用的宿主包、视图包和部署行。具体文件名由模板与包清单确定，职责如下：

| 部分 | 职责 |
|---|---|
| 应用声明与后端 | 身份、操作、协作需求、平台能力、业务规则、数据与后台工作 |
| 可选应用前端 | 业务页面、交互与页面上下文 |
| 测试与开发配置 | 验证业务行为，构建、部署与运行应用 |

第一版一个应用通常对应一个宿主包和一个可选视图包，仍使用同一 `appId`；不要求与单个 npm 包或底层插件一一对应。模板负责生成包，并登记 TypeScript 项目引用、构建入口、部署行、客户端注入、分层检查和测试路径，避免同一身份在多处手改。应用随部署组合加载，第一版不提供运行时从任意目录或 URL 安装。

前后端共享声明及其推导类型，运行依赖保持分离。前端通过统一接口调用后端，不直接导入数据库、凭据或后端运行对象；内部业务函数按需接入应用操作，不要求全部公开。

应用前端只通过平台绑定的应用操作、页面服务和应用设置接口访问后端；浏览器不能直接连接应用数据库、平台凭据、宿主文件或内部服务对象。前端请求的 `appId`、用户身份和权限由可信通道绑定，不能由浏览器 JSON 自填；后端返回按业务 Schema 和访问权限裁剪的数据。

应用自有文件由应用数据区或外部存储管理，按应用自己的格式、命名、删除、覆盖、导出和恢复规则处理，不随源码或部署产物删除。平台不提供通用的附件上传/下载或跨应用文件共享；应用不能读取任意本机路径、宿主工作区或其他应用目录。

浏览器访问外部网络不自动继承平台代理、应用凭据或平台身份；需要外部服务时由应用后端声明网络和凭据能力并代为访问。页面动作只改变导航、筛选、选择和草稿，持久业务写入必须调用应用操作并遵守统一权限、版本和幂等规则。

源码包与日常业务数据分离，数据位置仍由部署配置明确提供。移动源码、重建产物或删除开发副本不连带删除日常数据；源码绑定本身不授予日常数据访问权，开发会话须通过应用操作并按用户权限访问。自动化测试、候选构建和真实浏览器验收使用隔离验证实例（独立 `DSH_HOME`、profile、端口和工作区），避免把测试数据写入日常实例。应用需要接入外部系统时，在自身后端通过已声明并获授权的平台能力完成，不把外部系统另行注册为平台应用。

## 身份与调用接入

调用方身份、应用操作策略、用户设置和平台能力授权统一遵循[权限与调用](3-权限与调用.md)。运行时将可信入口绑定的身份传给同一调用服务；应用后端负责数据访问与业务校验。

应用自身前端、会话和其他应用共用操作实现，其他应用与会话共用同一用户策略，作者可按调用方类别声明默认。平台能力使用另行检查该应用的声明与授权，不能因某个应用操作无需确认就跳过检查；能力提供方式见[平台能力](5-平台能力.md)。

## 生命周期与后台工作

托管应用后端跟随启用状态运行：平台启动时启动已启用应用，运行中启用时启动对应后端。应用加载、可调用和界面可见是不同状态；启用后按启动流程加载，准备完成才接受应用操作调用，启动失败保留原因并回到停用状态，不自动重试。

应用是否已登记由应用记录是否存在表达，不再作为运行状态。登记后平台分别保存用户启用设置 `activation`（`enabled/disabled`）和运行状态 `runtime`（`stopped/starting/ready/stopping`），并可为非 ready 状态保存 `reason`，为 ready 状态保存 `health`（`ok/degraded`）。由部署组合登记的应用默认 `enabled + starting`，准备完成 `enabled + ready`；用户停用后进入 `disabled + stopping`，停止完成 `disabled + stopped`。独立来源应用（未来）默认 `disabled + stopped`，用户启用后才启动。启动失败为 `disabled + stopped` + `reason=platform.start-failed`；平台无法加载或运行（运行时、协议、依赖不兼容）为 `enabled + stopped` + `reason=platform.unavailable`；停止预算耗尽或清理失败为 `disabled + stopping` + `reason=platform.stop-incomplete`；更新期间为 `enabled + starting` + `reason=platform.updating`。只有 `activation=enabled` 且 `runtime=ready` 接受调用；`health=degraded` 仍接受调用，具体操作由应用在执行前检查前置条件，缺失时返回业务错误，平台不维护操作级状态列表。`stopped/starting/stopping` 不接受新调用，返回稳定的平台错误，不暴露内部进程状态作为业务契约。

应用可选声明业务健康检查，平台在启动、恢复或用户查询时按有限时长执行。检查只能读取应用状态和已配置依赖，返回 `ok/degraded/unhealthy`；平台映射为 `ready + health=ok/degraded`，或 `stopped + reason=platform.health-failed`。检查失败只更新状态并提供原因，不自动重启、切换依赖、修复配置或执行业务操作。

应用前端按需加载，打开页面读取已有状态，关闭页面或切换应用不停止后端、已有任务与有效订阅。应用启动应尽量轻量，昂贵资源按业务需要创建；第一版不提供首次调用自动启动或空闲自动停止机制。

应用自行判断运行必需条件与功能可选条件：缺少模型授权、缺少可选协作目标或可选数据只影响相关功能，应用可以通过 `health=degraded` 或操作前置条件报告；必需数据存储损坏、无法保证正常读写时启动失败，保留原数据，不创建空库冒充正常启动。平台不要求能力声明区分必需/可选，也不维护操作级可用列表。

应用按稳定类别声明能力并提供用途和受影响功能。新增能力默认未授权，撤回能力立即阻止后续使用；运行中的调用按实际结果结束或失败，不自动续跑。业务能力的声明、用户授权和凭据配置分别展示和检查，不能由运行时参数推断或互相替代；进程能力还要列出可执行文件、命令名称和用途，授权界面按此展示，声明用于审查而不是执行级白名单，平台不解释命令的业务语义；健康检查属于平台生命周期声明，不计入这项授权。能力声明保持简单的类别列表，不标记 `required`；应用在启动或健康检查中判断自身必需条件，平台只按声明提供入口。

用户重新启用、重载或修复配置后由平台显式执行恢复；平台不自动重启或重试，也不补做恢复前失败的调用、订阅通知或会话委托。恢复后各入口重新读取当前状态和声明，不能把旧错误当作成功。

平台升级时先校验所有已注册应用的运行时、协议和依赖兼容性；兼容应用按正常启动流程重新加载，不兼容应用为 `stopped` + `reason=platform.unavailable`，不强行启动或自动降级。平台升级不修改应用数据、应用设置、权限、凭据和订阅；后台任务无法续跑时记录为中断，不自动补跑。平台升级失败不覆盖业务数据，恢复平台版本后重新校验应用，也不自动恢复业务执行。

用户停用托管应用时执行可恢复的停止流程：先拒绝新工作，再请求在途直接调用和后台任务停止，最后暂停订阅并释放运行资源。直接调用按实际结果（`success/rejected/failed/cancelled`）或 `unknown` 结束；后台任务按取消或中断规则记录；已经发送到应用专用会话的消息由底层会话自行保留。超时或清理失败时报告停止未完成，`runtime=stopping` + `reason=platform.stop-incomplete`，不伪造成成功取消或自动重启；`activation` 保持 `disabled`，应用不接受调用。停用保留业务数据、应用设置、用户授权、凭据、订阅授权和平台记录；重新启用时重新校验并建立订阅、读取当前状态，不补发停用期间通知，不自动续跑旧任务。同一身份不能在旧实例未退出时再次注册。

## 注册、安装、更新与卸载

第一版应用随部署组合加载，不提供运行时从任意目录或 URL 安装。新增应用由开发入口生成包并登记部署；安装校验 `appId`、软件版本、运行时依赖和完整声明，校验失败不留下可调用的半成品。校验通过后展示应用身份、开放操作、平台能力和数据位置，启用只改变 `activation`，不自动授予其他权限。支持独立应用来源时，需要额外的加载器、来源校验、注册表和信任模型，另行设计。

更新沿用同一 `appId`，保留业务数据和用户设置；新增能力、订阅和凭据仍需用户单独处理。平台可以先校验候选版本，再由用户明确确认加载；更新期间拒绝新调用，已有调用和后台任务按实际结果、取消或中断记录。应用负责自己的数据备份、迁移和恢复，平台不提供通用迁移协议、兼容判断或自动回退；加载失败时保留数据并报告失败原因。

开发会话修改源码不会自动替换日常运行版本。构建并加载默认作用于隔离验证实例；把候选版本应用到日常实例是单独的明确动作，需用户确认并遵守更新、备份与迁移规则。源码和业务数据的备份、迁移与恢复由开发者负责。平台不提供多版本回退历史，是否支持回退由应用自己的版本和数据规则决定。

卸载停止应用并停止后续调用和订阅，默认保留业务数据与平台记录；清理数据由用户单独决定。第一版不提供运行时卸载，从部署组合移除应用按同一停止与保留规则处理；具体安装、卸载、重新关联和迁移细节等出现真实需求后再扩展。

后台工作归应用，使用应用自己的能力与权限。后台任务没有用户交互，需要确认的操作返回 `rejected` + `platform.confirmation-unavailable`，不能把页面或会话的确认带入任务。应用负责业务任务去重、并发控制和取消；超过应用自身上限时返回业务错误。统一任务记录提供 `taskId`、所属应用、来源 `callId`、状态、最新进度、可选业务对象引用和取消入口；平台只施加统一的请求、执行时长、资源和传输硬限制，不提供通用队列、计费或跨应用配额。业务结果仍归应用持久数据。任务状态采用 `running/cancelling/succeeded/failed/cancelled/interrupted`，取消入口的受理与终态规则遵循第 2 篇；页面应区分“取消请求已受理”和“任务已取消”。

启动、查询与进度的结果语义见[耗时操作与进度](2-统一JSON协议.md#耗时操作与进度)。关闭页面不取消已受理的后台工作；重新打开按权限查询已有任务与结果，不重新提交。

平台不提供自动重试、跨重启续跑、通用定时任务编排器、cron 中心、可靠消息队列或业务流程引擎。应用可以自行维护定时工作，但需要通过应用设置或持久授权明确建立，并必须使用应用生命周期和已获准能力；任务状态和取消沿用统一后台任务，不能据此自动发起会话委托或绕过操作确认。应用停用、更新或缺少必要能力时，定时工作暂停或失败，平台不自动补跑错过的触发；恢复后是否基于当前状态补偿由应用决定，并须使用新的任务记录，不能伪装成原次执行。将来需要可靠调度时另行设计持久计划、时区、错过触发和去重语义。

## 数据与工作区

| 数据 | 负责方与边界 |
|---|---|
| 业务数据、应用设置、业务恢复 | 应用后端；默认使用平台标准存储，特殊数据可使用声明的独立文件、数据库或外部服务 |
| 应用注册、操作策略设置、订阅授权、平台能力授权、应用模型选择、运行记录 | 平台保存；设置与授权由用户管理，范围见[权限与调用](3-权限与调用.md#用户与访问边界)，不从调用历史推断有效授权 |
| 会话历史、工具审批 | 底层平台会话体系 |
| 会话交接材料 | 底层会话历史与应用自己的页面草稿；不代替业务数据 |
| 应用模型调用记录与统计 | 平台；身份、状态与用量归属见[模型调用](5-平台能力.md#平台统一模型接口) |
| 页面状态和草稿正文 | 应用前端管理，持久化由应用负责；不把运行服务对象写入状态 |
| 页面草稿共享记录 | 平台保存 `pageId`、`draftId`、字段范围、`revision` 和会话标识，不保存草稿正文；正文仍归应用编辑器 |
| 凭据 | 平台凭据或按应用隔离的 secret 存储；应用凭据由用户管理，不混入业务导出与页面上下文 |

**应用与工作区独立。** 工作区只是显式使用的目录；切换它不改变应用的数据、操作策略与平台能力授权。会话工作区决定文件工具的目录，开发会话使用本仓源码根，并以该应用的宿主包、视图包和部署行为焦点；文件工具仍可访问整个仓，这是工作区约定，不是文件系统沙箱。需要目录的 Git、磁盘或回顾操作显式接收目标，不能隐式把全局当前目录当作业务分区。

平台为应用提供按 `appId` 隔离的标准存储 API。应用通过受限存储句柄使用文档、分页集合、版本写入和事务，不能取得数据库连接或访问其他应用的数据分区。标准存储负责一致性、并发版本、整库备份和按应用恢复；应用仍拥有数据结构、业务校验、对象语义、导入导出和迁移规则，Schema 校验不能代替业务完整性检查。

应用可以声明独立文件、数据库或外部服务作为特殊存储。此时应用负责该存储的一致性、位置、备份、恢复和损坏处理，平台只记录声明并在管理界面展示边界，不把外部存储伪装成标准存储。即使应用使用相同的外部存储，应用之间也通过操作访问数据，不直接读取对方的表或文件。

凭据与存储的接入边界见[平台能力](5-平台能力.md#存储凭据与进程)。应用声明数据归属与存储方式，实际位置由明确配置确定；宿主数据位置由部署配置注入，不在模块加载时猜路径。平台提供统一管理入口，展示标准存储或外部存储的位置、备份说明与应用支持的导入导出操作。

备份用于恢复某个时点的数据，须遵循对应存储的一致性要求；不能在数据库写入过程中任意复制文件就报告备份成功。标准存储由平台提供一致性备份、按应用恢复和损坏保护；外部存储由应用提供相应实现并在声明中说明范围。平台提供查看数据位置、备份状态、备份恢复、业务导出与导入入口，但不猜测应用的业务结构。恢复只处理应用业务数据，不恢复权限、凭据、订阅或会话身份；恢复必须选择明确备份或导入文件，先停用应用、排空在途工作、校验格式并保留当前数据备份；失败不覆盖当前数据。导出提供可理解、可迁移的业务内容，格式与导入校验由应用定义，不要求包含缓存或内部索引，不包含凭据，也不通过业务导入恢复权限或会话身份。清理应用数据、应用凭据和平台运行记录分别确认，卸载不自动清理；第一版不提供跨应用统一事务、一键迁移全部应用数据或自动保留策略。

应用负责业务导入、导出和迁移语义；平台不猜字段、不跨应用合并，也不因业务数据清理删除日志、调用记录或已发送会话消息。已删除或不可访问对象的相关记录按各自保留规则展示，不伪造对象仍存在或操作已成功。

应用对可能重复的业务写入自行设计幂等字段、目标版本或业务去重规则；平台不把 `callId` 当作幂等键。读操作可重新查询当前状态，写操作在结果未知时由应用提供状态查询或冲突处理，不能默认再次执行。业务去重记录归应用数据，按应用的恢复与导出规则处理。

应用前端、会话、后台任务和其他应用写入同一对象时，统一使用应用定义的业务版本与冲突规则。页面草稿的 `revision` 只保护草稿，不代替业务对象版本；不需要版本保护的操作由应用明确承担追加或最后写入语义。跨应用没有平台级事务，多个应用分别成功或冲突时由业务流程记录和补偿，不回滚已发生效果。

平台调用历史、诊断日志和已发送会话消息分别按各自规则保留和查询；业务数据清理不自动删除平台记录，也不让应用读取平台全局审计。记录中涉及已删除或不可访问对象时展示“对象已删除／不可访问”，保留关联所需的元数据但不暴露原正文。第一版不提供跨应用审计查询、全文搜索或从日志恢复业务数据。

导入和导出由需要它的应用负责格式校验、版本转换、对象 ID 冲突和外部引用处理；这类功能遵循应用操作的确认和业务校验。平台不提供跨应用对象打包、全局 ID 重写、引用自动修复或跨应用事务。

运行中替换数据需暂停目标应用的新工作、排空在途操作、校验基线并备份；替换后重新加载，再恢复可用。不可读或损坏的数据不能被当作空数据覆盖；应用停用、卸载和源码重构不删除业务数据。

## 记录与验证

| 概念 | 表达什么 | 关联与边界 |
|---|---|---|
| 调用结果 `Outcome` | 一次调用的成功、拒绝、失败、取消或未知，协议见第 2 篇 | `callId` 用于关联；启动任务成功不代表任务完成 |
| 后台任务 | 应用拥有的持续工作、进度与取消状态 | `taskId` 标识任务，关联来源调用；业务结果由应用保存 |
| 会话委托 | 页面把准备好的内容交给应用专用会话 | 会话消息和页面上下文按[会话委托](9-会话委托.md)的简单路径关联 |
| 操作历史 | 调用来源、目标与结果的排错记录 | 可以不完整，不能替代业务数据、授权或会话消息 |

基本调用历史保留调用方、目标、时间、状态和公开错误，默认不保存全部参数与结果。历史写入失败报告诊断，不把已经成功的应用操作改判失败；会话消息由底层会话负责保存，不能用调用历史代替会话记录。

## 日志与诊断

平台记录应用生命周期、调用、任务、订阅、模型和进程的结构化元数据，并绑定 `appId` 及可用的 `callId`、`taskId`。平台不默认保存完整输入、输出、模型提示词、业务正文或页面上下文；日志是排查材料，不是业务数据、备份或会话记录。

应用可以写结构化诊断日志，平台自动绑定应用身份和可信关联标识。日志与业务数据分开，应用不能通过日志接口读取或写入其他应用内容。凭据、代理密钥、完整模型提示词和响应、页面上下文中的敏感字段不得进入日志；应用负责业务字段脱敏，平台拒绝或清理已识别的受保护字段。

用户看到应用可用状态、必要错误和有限的诊断摘要。应用开发会话只在明确绑定的应用运行实例中查询详细日志；应用专用会话不会自动获得日志全文，应用须通过明确操作提供诊断结果。日志查询失败不改判已经完成的业务调用，平台不做远程遥测或自动上传，日志按有限期限保留并可独立清理。

验收需证明：身份不能由 JSON 冒充；注册校验不留下可调用的半成品；应用接入外部系统时仍遵守声明、凭据、网络和操作权限边界；更新保留数据与用户设置，新增能力不自动授权，失败不覆盖原数据；卸载默认不删除业务数据与凭据；操作策略与平台能力授权的变更约束后续使用；已启用应用无需打开页面即可运行，缺少可选条件只影响相关功能；切换页面或工作区不改变应用数据；停止未结束时如实报告；损坏存储不被覆盖。
