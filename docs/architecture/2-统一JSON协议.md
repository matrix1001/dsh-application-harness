# 统一 JSON 协议

> 类型：目标设计。当前实现与差异见 [11 §5](11-实现与验收.md#5-当前未完成与边界)。

[总体设计](1-总体设计.md) · [用词约定](1-总体设计.md#用词约定) · 本篇是所有设计共用的数据协议。以下为目标接口，不是当前源码签名。

## 统一什么

跨应用调用、会话调用应用、应用前端调用应用后端，使用同一份应用操作声明、请求和结果。应用前端将用户的输入变为 JSON，将结果呈现为页面内容；用户不需要手写 JSON。

JSON 统一数据语义，不规定组件布局，也不要求同进程调用反复序列化。底层平台通信和工具协议负责传输包装：页面、应用和服务方法使用完整 `Outcome`；模型工具面可以在成功时返回结果本身、失败时返回稳定错误码与“可能已有副作用”的含义，但不能只保留自然语言错误或把失败改写成成功。

| 数据类别 | 共用内容 | 专属结构定义 |
|---|---|---|
| 应用操作调用 | 请求、`Outcome`、Schema、`ObjectRef` | 本篇与各应用操作声明 |
| 对象展示、业务变化 | JSON 值、Schema、`ObjectRef` | [应用互联](6-应用互联.md) |
| 页面、动作、草稿 | JSON 值、Schema、`Outcome`、`ObjectRef` | [页面交互](7-页面与人机交互.md) |
| 委托与结果 | JSON 值、Schema、`Outcome`、`ObjectRef` | [会话委托](9-会话委托.md) |

页面与委托是平台服务，不伪装成业务应用。它们有自己的服务方法和输入，结果复用 `Outcome`；页面快照和事件通知是数据，不强行包成业务调用。

## 基础类型

| 类型 | 唯一规则 |
|---|---|
| `JsonValue` | 标准 JSON 的对象、数组、字符串、有限数字、布尔值、`null` |
| `ObjectRef` | `{ appId, type, id }`，三个必填非空字符串；只定位业务对象，不包含平台实例字段 |
| `SessionRef` | `{ workspaceId, sessionId }`，两个必填非空字符串，定位绑定用户的平台会话 |
| `Schema` | 平台声明 DSL 及其导出的 JSON Schema（第一版受限子集）；输入、结果、页面与事件复用同一校验器及公共定义 |
| `Outcome` | 下文定义的成功、拒绝、失败、取消或未知结果；不是后台任务或会话的状态机 |

禁止函数、类实例、循环引用、`undefined`、`NaN` 和无穷数。大整数用有业务含义的字符串；对象 ID 使用字符串；日期用 `YYYY-MM-DD`，时刻用带时区的 RFC 3339 字符串。大列表分页，大文件由应用数据区或外部存储管理，不把本机路径当作读取凭据。

第一版不提供平台文件资源；应用自有文件由应用数据区或外部存储管理，按应用自己的格式、备份、恢复和导出规则处理，不通过业务 JSON 传递本机路径、共享目录或公共 URL。

`ObjectRef` 不包含展示名、授权、业务版本或 `instanceId`；第一版一个宿主内每个 `appId` 只有一个平台应用实例，也不在协议中表达多账户或业务空间。这些信息由所属应用按权限提供。页面快照 ID、业务版本、调用 ID 和会话标识各有用途，不能互相代替。

业务导出可以包含应用自己定义的 `ObjectRef` 和外部 `ObjectRef` 关联，但引用仍按原 `appId/type/id` 解释。导入环境没有对应应用或对象时，平台保留引用并报告不可解析；不改写 ID、不按名称猜测替代对象，也不自动创建其他应用对象。

## 应用操作请求

```json
{
  "appId": "tasks",
  "operation": "create",
  "input": { "title": "准备季度报告" }
}
```

外层恰好包含这三个字段：`appId` 与 `operation` 是明确目标，`input` 是对象，无参数用 `{}`。已绑定目标的工具或客户端方法可只接收 `input`，接入层从固定绑定补齐目标。不能根据输入搜索或替换目标应用。

身份、权限、交互上下文、取消信号和进度出口由可信接入层提供，不能放进业务请求冒充授权。交互上下文只用于选择确认承载，不能由业务 JSON、页面上下文或模型输出设置，规则见[调用与确认](3-权限与调用.md#交互上下文与确认承载)。第一版所有用户发起的页面、会话和平台管理入口都必须绑定用户；应用间调用保留来源应用身份，但只能在用户已授权的实例范围内执行。底层共享访问者不能因此获得本平台的用户身份。传输如何关联并发响应由接入层负责。

跨应用调用由平台生成不可伪造的调用链上下文，至少关联当前 `callId`、来源应用、目标应用和深度。应用只能读取与自身调用相关的最小来源信息，不能修改调用链、冒充上游身份或把业务字段当作链路凭据。同步调用及其启动的后台任务沿用来源链，后台任务另有 `taskId`；查询结果不重复扩展调用链。

平台对请求体、结果体、单次执行时长及传输缓冲施加统一硬限制；超过限制直接返回明确的错误结果，不排队、不自动重试。具体数值属于运行配置，不写入业务 Schema；应用需要更大内容时使用分页、后台任务或自己的数据区。

平台运行记录只保留排错和关联所需的最小元数据，例如应用、来源、目标、时间、状态、错误代码和关联 ID；默认不保存完整业务输入、输出、模型提示词或页面正文。业务对象删除后，记录中的引用可以保留但必须按不可解析状态处理，不能继续提供已删除正文。

平台拒绝循环目标、超过固定深度或重复调用链，返回明确的 `platform.call-chain-limit` 错误，不自动改目标、不重试。订阅通知是独立触发，不沿用发布方原调用链；订阅方响应时生成新的调用链，仍执行同样限制。

应用结果、业务正文、页面上下文、通知和外部资料进入会话或模型时一律作为数据，并保留来源应用、操作和时间。结构化字段不能改变会话工具范围、平台权限、用户确认或系统规则；应用不能通过结果 JSON 要求会话跳过确认、调用其他应用或泄露凭据。

## 统一结果 Outcome

| `status` | 内容 | 含义 |
|---|---|---|
| `success` | 必填 `result`，任意符合声明的 JSON 值 | 操作定义的工作完成，输出通过校验 |
| `rejected` | 必填 `error` | 操作未执行：目标、身份、范围、声明、输入或可用性检查未通过；可视为没有业务副作用 |
| `failed` | 必填 `error` | 操作已执行或部分执行；不保证没有副作用 |
| `cancelled` | 必填 `error` | 本次调用被停止；不撤销已发生的业务效果；已经完成则返回实际结果，不伪造取消 |
| `unknown` | 必填 `error` | 无法可靠确定是否执行或最终结果；不等于失败或未执行 |

五个分支互斥：成功必须带 `result`，其他状态必须带 `error`，不能同时带两者。无返回内容的成功使用 `result: null`。运行时为每次调用生成 `callId` 并返回；入口尚未获得 ID 时产生的结果可省略，已保存的非调用结果也不虚构 ID。`callId` 只用于关联，不是去重或授权依据。

平台不为一般应用操作提供通用幂等或自动去重。写操作在 `unknown` 后不能仅凭原 `callId` 盲目重做；调用方应先查询业务状态，或使用应用声明的请求号、外部事件 ID 等业务幂等字段。应用负责保存和校验这些字段，声明是否支持重复提交、冲突处理和状态查询；平台不猜测其语义。需要批量结果时，由应用在自己的结果中表达每项状态，不新增平台级影响收据。

并发控制属于应用业务语义，平台不为所有对象提供全局锁或自动合并。需要保护的写操作由应用声明并校验 `expectedVersion` 或等价业务版本；版本不匹配返回明确的业务冲突错误，并按权限提供当前对象引用和版本信息。调用方应重新读取当前状态后决定合并或重新提交，平台不自动覆盖、重试或让模型猜测合并。

平台诊断记录可以使用 `callId`、`taskId` 关联一次调用或后台工作；会话交接沿用会话自身的消息和会话标识，不新增平台级委托结果标识。关联标识由可信接入层生成或绑定，应用不能在业务 JSON 中自填身份来获得关联或权限。跨应用调用各自拥有调用标识，平台诊断记录保留它们之间的来源关系；关联记录不改变各自的 `Outcome`、授权或重试规则。

```json
{
  "callId": "call-001",
  "status": "success",
  "result": {
    "task": { "appId": "tasks", "type": "task", "id": "123" },
    "title": "准备季度报告"
  }
}
```

`error` 的公共字段：

| 字段 | 规则 |
|---|---|
| `code` | 必填稳定字符串；平台用 `platform.` 前缀，业务用 `app.` 前缀 |
| `message` | 必填可读说明，可本地化；程序不解析文案判断状态 |
| `details` | 可选 JSON 对象，按错误声明表达字段位置、已知影响或对象引用 |

```json
{
  "callId": "call-002",
  "status": "rejected",
  "error": {
    "code": "platform.invalid-input",
    "message": "任务标题不能为空",
    "details": { "field": "/title" }
  }
}
```

`status` 说明执行事实，`error.code` 说明原因：`rejected` 表示操作没有执行，调用方可以按“没有业务副作用”处理，但仍按具体错误码决定提示或修正输入；`failed` 表示操作已经执行或部分执行，可能已有副作用，不保证回滚。

`cancelled` 表示调用被停止，取消是请求，不撤销已发生的业务效果；`unknown` 专门表示无法可靠确定是否执行或最终结果，不等于失败或未执行。

调用方以 `status` 判断执行事实，不能仅凭错误码或缺少 `details` 推断 `failed` 已回滚或 `unknown` 未执行；需要说明已知部分影响或相关对象时，由稳定错误码和 `error.details` 如实表达。字段位置使用相对于 `input` 的 JSON Pointer。平台可以在内部诊断记录中保存执行阶段，但不把它作为公共 `Outcome` 字段。

```json
{
  "status": "unknown",
  "error": {
    "code": "platform.connection-lost",
    "message": "连接中断，无法确认任务是否已创建"
  }
}
```

平台稳定错误至少覆盖以下类别（均加 `platform.` 前缀）：目标与操作 `unknown-app`、`unknown-operation`、`unavailable`、`starting`、`stopping`、`updating`；调用链 `call-chain-limit`；权限与确认 `denied`、`confirmation-unavailable`。

输入输出 `invalid-input`、`invalid-result`、`execution-failed`、`cancelled`、`connection-lost`；页面与草稿 `page-unavailable`、`stale-snapshot`、`action-not-allowed`、`draft-not-shared`、`draft-scope`、`draft-conflict`；模型 `model-limit-exceeded`。

错误码说明原因，`status` 说明是否执行；平台按实际阶段选择状态，例如 `invalid-input` 通常是 `rejected`，`execution-failed` 是 `failed`，`connection-lost` 无法确认时是 `unknown`。

应用声明需要调用方处理的业务错误与详情 Schema，不泄露内部堆栈或凭据。

应用可用性由平台提供 `activation`、`runtime`，以及可选的 `health` 和 `reason`：

| 字段 | 规则 |
|---|---|
| `activation` | `enabled/disabled`，表示用户是否启用 |
| `runtime` | `stopped/starting/ready/stopping`，表示当前运行 |
| `health` | `ready` 时可取 `ok/degraded`；`degraded` 表示可选条件缺失，仍接受调用，具体操作由应用在执行前检查前置条件并返回业务错误 |
| `reason` | 可选 `{ code, message }`，说明 `starting/stopping/stopped` 的原因；至少覆盖 `platform.updating`、`platform.start-failed`、`platform.health-failed`、`platform.unavailable`、`platform.stop-incomplete` |

应用登记记录存在但 `activation=disabled` 时不可调用；只有 `activation=enabled` 且 `runtime=ready` 接受调用，`health=degraded` 不阻止调用。状态按场景取值：

- 更新期间：`enabled + starting` + `reason=platform.updating`，拒绝新调用并返回 `platform.updating`；
- 平台无法加载或运行（运行时、协议、依赖不兼容）：`enabled + stopped` + `reason=platform.unavailable`，不自动重试；
- 启动失败：`disabled + stopped` + `reason=platform.start-failed`，保留原因；
- 停止预算耗尽或清理失败：`disabled + stopping` + `reason=platform.stop-incomplete`，不伪造成功取消，用户可重试停止。

由部署组合登记的应用默认 `enabled + starting`，准备完成 `enabled + ready`；用户停用后 `disabled + stopping`，停止完成 `disabled + stopped`。独立来源应用（未来）默认 `disabled + stopped`，用户启用后才启动。

调用方只依赖 `activation`/`runtime` 和 `reason`，不依赖内部进程细节；页面、会话和其他应用看到同一状态，错误详情按访问权限裁剪。

应用可声明只读的业务健康检查，返回 `ok/degraded/unhealthy` 与必要原因；平台把 `ok`/`degraded` 映射为 `ready + health=ok/degraded`，把 `unhealthy` 映射为 `stopped + reason=platform.health-failed`。检查结果供平台判断状态，不能由应用直接伪造平台状态。健康检查必须轻量并有时限，不执行迁移、网络扫描、模型调用或业务写入，也不自动修复或触发会话。

输入错误、权限拒绝不进入业务实现，返回 `rejected`；业务执行中的明确失败返回 `failed`，副作用无法确认返回 `unknown`；确实停止才返回 `cancelled`，已经完成则返回实际结果，不撤销既有业务效果。抛错或非法输出不得返回成功。所有结果都不触发自动重试。

## 耗时操作与进度

普通操作直接返回业务结果；需要脱离当前请求持续运行的工作采用启动与查询。`Outcome` 始终表达一次操作的结果，不增加 `running`、`pending` 或 `progress` 分支。

| 操作 | 成功的 `result` | 成功含义 |
|---|---|---|
| 直接完成业务操作 | 业务结果 | 操作定义的工作已完成 |
| 启动后台工作 | 包含 `taskId` 的已声明结果 | 任务已建立，不代表后台工作已完成 |
| 查询后台任务 | 当前任务状态与可用的结果信息 | 查询成功，任务本身仍可能运行、失败或中断 |

操作名称与说明须明确完成边界，例如“启动报告生成”只承诺建立任务。页面、其他应用与会话按同一含义理解结果，不能把启动成功展示或解释为报告已生成。

进度是可选信息，用于展示当前进展；通知丢失不改变最终结果，进度达到 100% 也不能代替明确完成状态。进度与最终业务结果分别处理。

后台任务使用 `taskId`，生命周期与页面独立性见[应用运行](4-应用结构与运行.md#生命周期与后台工作)；会话交接使用会话消息和页面草稿，规则见[会话委托](9-会话委托.md)。两者共用 JSON 与 `Outcome` 语义，保留各自状态和归属规则，不合并为通用任务系统。

后台任务的取消入口是控制请求，不把取消请求成功解释为任务已经取消：成功只表示请求已受理或返回当前状态。任务从 `running` 进入 `cancelling`，确认后续工作已停止才进入 `cancelled`；取消过程中已经 `succeeded` 或 `failed` 的保留真实结果，无法确认最终状态时进入 `interrupted`。重复取消返回当前状态，不再次启动或停止工作；取消不回滚已发生的业务效果，也不自动重试或创建新任务。

平台不因后台任务提供通用队列、计费或自动限流；应用负责业务任务的去重、并发控制和取消。超过应用自身上限时由应用返回业务错误，超过平台硬限制时由平台返回平台错误。

平台只对自身协议动作提供必要的重复提交保护，例如同一导入任务使用明确的 `taskId`；这类保护不扩展为所有业务操作。第一版不提供全局幂等键、跨应用事务或恰好一次执行保证。

定时或外部触发的后台工作仍使用同一任务协议，但触发来源由可信运行层记录，不能由业务 JSON 冒充用户决定。触发建立任务不改变 `Outcome`、权限或委托规则；错过触发不自动生成补发任务。通知中的 `eventId` 不是任务去重键，业务重复处理仍由应用负责。

## 应用操作声明与 Schema

应用作者维护一份可校验、可推导 TypeScript 类型的代码声明，用于前后端类型推导，并由平台确定性地导出标准 JSON Schema 与操作说明，供运行时校验、会话和其他应用使用。不要求作者手写导出的 JSON Schema，也不分别维护业务类型、校验规则和对外声明。声明源复用平台现有的 `ParameterSchemaSpec`/`ValueSchemaSpec`，类型推导使用 `InferArgs`/`InferValue`；平台提供 `defineOperation` 泛型辅助，把同一份 schema 推导到 `execute` 的输入和结果类型。不引入第二套 schema 库。

操作名称、用途、读写性质和开放策略由开发者声明或采用协议规定的默认值，不由模型推测。业务函数接收业务输入、返回业务结果；平台负责输入输出校验和公共 `Outcome` 包装。公共请求、结果与引用结构由平台维护，应用补充自己的业务结构与语义。

导出的操作声明包含以下公共字段，运行函数单独绑定，不能序列化进声明：

| 字段 | 规则 |
|---|---|
| `operation`、`description` | 应用内唯一名称、清楚的业务用途 |
| `effect` | `read` 或 `write`；generation 2 的新声明必填，generation 1 缺省按 `write`。读取不得修改业务状态或产生外部副作用 |
| `exposure` | 作者按调用方类别声明的默认值：`{ ai?, peers? }`，每项为 `closed/open/confirm`（不开放、默认无需确认、默认需要确认），省略的类别为 `closed`。`ai` 指普通、应用区和开发会话，`peers` 指其他应用及其后台调用。用户对每个操作只维护一条覆盖策略，规则见[权限与调用](3-权限与调用.md) |
| `inputSchema`、`resultSchema` | 分别校验 `input` 和成功的 `result` |
| `errors` | 可选，按业务错误码声明说明与 `detailsSchema` |

声明源码使用平台 DSL 的 `params`/`result`；导出的公共声明字段为 `inputSchema`/`resultSchema`，两者由同一份声明生成。

例如，导出的 `tasks.create` 操作声明：

```json
{
  "operation": "create",
  "description": "创建任务并返回任务引用",
  "effect": "write",
  "exposure": { "ai": "confirm", "peers": "open" },
  "inputSchema": {
    "type": "object",
    "additionalProperties": false,
    "required": ["title"],
    "properties": { "title": { "type": "string" } }
  },
  "resultSchema": {
    "type": "object",
    "additionalProperties": false,
    "required": ["task", "title"],
    "properties": {
      "task": {
        "type": "object",
        "additionalProperties": false,
        "required": ["appId", "type", "id"],
        "properties": {
          "appId": { "type": "string" },
          "type": { "type": "string" },
          "id": { "type": "string" }
        }
      },
      "title": { "type": "string" }
    }
  }
}
```

示例中的 `exposure` 表示：AI 会话调用 `create` 默认需要确认，其他应用调用默认无需确认；作者将某个类别声明为 `closed` 时，用户设置不能把该类别改为开放。用户覆盖与执行规则见[权限与调用](3-权限与调用.md)。

示例中的 `ObjectRef` 由平台公共定义内联生成，开发者不手抄。第一版声明源使用平台 `ParameterSchemaSpec`/`ValueSchemaSpec`，导出为同一份声明生成的标准 JSON Schema；支持对象、数组、标量、`required`、`additionalProperties`、`enum/const`、`oneOf`。不支持长度、格式、数值范围、`anyOf`、`$defs/$ref`；这些业务约束由应用在 `execute` 中校验，声明与导出都不承诺它们。各 Schema 独立可解析，不依赖运行时网络引用。

应用声明可以声明 `objectTypes`。`pages`/`pageActions` 声明在 v1 延期；当前应用页面由视图自身路由，页面服务仍使用固定动作，不按声明校验 view/action。

对象类型声明包含描述和只读解析操作；调用方可以省略 `view`，由应用选择默认页面；没有页面时不能通过当前应用页面入口打开。

`objectTypes` 为可跨应用传递的对象类型登记解析操作：

| 字段 | 规则 |
|---|---|
| `type` | 应用内唯一的对象类型名，与 `ObjectRef.type` 一致 |
| `resolveOperation` | 已声明的只读应用操作；按真实身份、访问范围和该操作的确认策略执行，输入为对象 ID，不能另设绕过权限的解析通道 |

解析成功只返回 `ref`、`title` 和可选的 `summary`，不因解析引用扩大读取范围，也不把摘要当作完整业务对象。对象类型和页面声明随应用版本发布，不另建对象注册中心；对象如何在自己的页面中打开由应用决定。声明变化后按当前声明重新校验原有绑定，不自动转换或猜测修复。

公开对象默认明确拒绝未知字段；需要扩展数据时声明专用字段与 Schema。平台不静默类型转换、删参数或填默认值。业务合法性仍由应用判断；统一工具入口的通用参数不降低每个操作的运行时校验。

## 版本与边界

平台公共协议使用 `protocolVersion`，与应用软件版本分开；应用发布新版本不必改变平台协议。第一版不对应用间操作、事件、对象或页面再叠加运行时契约版本。

| 版本 | 范围与变化条件 |
|---|---|
| `protocolVersion` | 平台公共请求、结果与引用等统一格式，初始为 `1`；公共协议发生不兼容变化时增加 |

跨应用 `calls` 声明目标应用和操作；当前实现接受 `AppId | { app, ops }`，字符串形式表示目标全部已开放操作；事件只声明来源应用和类型。

调用时校验目标应用当前声明、开放策略、输入和业务规则；操作不存在返回 `platform.unknown-operation`，输入不匹配返回 `platform.invalid-input`，含义变化由构建、声明校验和测试保证。页面和对象使用当前声明，视图或操作不存在时返回明确错误。

应用更新不会替依赖方自动升级声明；依赖方须显式更新并重新校验。安装与更新同时校验平台运行时、协议、依赖和完整声明；不满足时应用不可启用，不自动降级、改写声明或建立兼容层。

平台升级前后按同一规则重新校验已注册应用的运行时、`protocolVersion`、依赖和声明。平台公共协议发生不兼容变化时提升 `protocolVersion`；不兼容应用保持 `stopped` + `reason=platform.unavailable`，不强行启动。平台升级不改变应用数据、应用设置、用户权限、凭据或订阅，也不提供多版本平台并行或长期兼容窗口。

普通页面与会话工具接入使用当前声明建立绑定，声明变更后原绑定失效；旧声明下已准备但尚未执行的调用及其确认不能直接沿用。会话可重新读取当前声明，按新声明准备新的调用并遵守当前确认策略。目标选择、身份与确认规则见[权限与调用](3-权限与调用.md)。`protocolVersion` 放在注册与连接元数据中，不在每个业务输入重复。

## 验收约束

- 相同应用操作从页面、应用、会话三个入口调用，结果结构与业务校验一致；其他应用与会话遵守同一用户策略，作者对 AI 与其他应用可分别声明默认，各入口仍校验真实身份与范围。
- 非法输入不执行；非法输出不成功；拒绝、失败、取消和结果未知不被混淆；没有自动重试。
- `rejected`、`failed`、`cancelled` 与 `unknown` 的含义清晰区分；调用方不从缺少错误详情推断未执行或可回滚，应用按需在业务错误详情中说明已知部分效果。
- 启动成功、查询成功与后台工作完成明确区分；进度不作为完成凭据，各入口使用相同结果语义。
- 公共引用与 Schema 只有一个定义来源；类型推导、导出的 Schema 与运行时校验来自同一声明，所有示例、工具适配及输出都通过同一协议验证。
- 声明更新后，旧绑定和旧确认不能用于执行新声明；操作、视图或对象类型不存在时返回明确错误，兼容性同时考虑数据结构与业务含义。
